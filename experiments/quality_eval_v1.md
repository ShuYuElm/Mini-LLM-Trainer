## 评估问题与任务构成

已有验证 loss 衡量给定参考答案的预测表现；本轮要进一步观察自由生成是否
保留必要信息、正确执行指令，以及避免添加要求或编造事实。
对比已有 Base、r=8、r=32，使用相同输入、greedy 解码、输入上限 256 tokens
和输出上限 128 个新 tokens。无需新增训练。

| 类别 | 题数 | 检查重点 | 预先保存的自动检查目标 |
| --- | ---: | --- | --- |
| 摘要 | 8 | 日期、地点、适用范围、例外与后果 | 无，按语义人工判断 |
| 改写 | 8 | 角色、期限、请求/拒绝意图、不新增任务 | 无，按语义人工判断 |
| 信息提取 | 8 | 字段、数值、角色、缺失值、布尔类型 | JSON 对象及准确值类型 |
| 格式遵循 | 8 | 行数、排序、筛选、大小写、分隔符 | 指定的完整输出行 |
| 简单推理 | 8 | 多步算术、向上取整、时间、单向逻辑蕴含 | 无，人工检查答案与理由 |

这些任务由编码助手为本项目编写，设计时已知旧六题的表现，但没有生成或查看
新四十题的目标模型回答。参考答案也是合成的，不能视为权威 benchmark 标注。
人工评分接受满足条件的等价表述，不要求摘要、改写或推理逐字匹配参考答案。

## 评分与盲评协议

每个回答按四个维度分别打 0、1、2 分，并记录简短理由：

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 正确性 | 主要答案错误、矛盾或不可用 | 部分正确但存在事实/推理错误 | 相关事实与推理正确 |
| 完整性 | 缺失主要要求 | 包含主旨但遗漏部分必需信息 | 覆盖每条必需信息 |
| 格式遵循 | 严重违背要求 | 大体遵循但有小问题 | 满足所有明确格式要求 |
| 无无据添加 | 编造重要事实、增加任务或改变意图 | 有不影响主旨的小幅多余添加 | 无无据事实或额外要求 |

缺失信息主要记在完整性；说错的信息记在正确性。同一问题可能影响多个维度，
因此四个维度不是彼此独立的统计量。优先报告各维度和各类别分数，保留逐题理由，
不要只展示一个总分或挑选成功样例。

下一步生成时，每题为三个回答随机安排匿名顺序；评分文件不显示模型名称。
模型与匿名回答的映射单独保存，评分完成后再揭示。评分者仍可能从文风猜到模型，
这只能降低身份偏见，不能保证完全盲法。生成入口已按这一协议导出
`quality_review_blind.json` 与 `quality_review_mapping.json`。

JSON 检查拒绝代码围栏、额外字段、错误值及错误类型；字段顺序不影响通过。
固定行检查允许外层空白与平台换行差异，内部文字、顺序与分隔符需符合要求。
自动格式检查在报告中单独给出通过数与分母，不代替四维人工评分。

## 版本与重复检查

v1 的规范化 JSON SHA-256 为：

```text
c6d0fce2304cc0fe576af3c78d4bcd266a27b9e1a1c2bfce468a35f55b0a06ec
```

该哈希覆盖题目、参考答案、评分标准、生成设置和评审协议，不受 JSON 缩进、
键顺序或文件换行影响。生成结果时应保存这个哈希。若查看回答后改题或改评分标准，
需建立新版本并说明原题已参与开发，不能将修改后的集合继续当作未接触的评估集。

2026-09-21 检查了固定的 2,000 条训练数据、200 条验证数据和原有 6 个开发提示词：

- Unicode NFKC、大小写统一、忽略标点和多余空白后，比较完整 instruction + input。
- 额外比较规范化后至少 40 个字符的 input，避免更换指令后漏掉相同材料。
- 近似匹配要求词三元组 Jaccard 相似度至少 0.35，且共享三元组至少 8 个。
- 在这些规则下发现 **0 条匹配**；报告保存了比较语料的规范化内容哈希。
- 使用缓存的 Qwen tokenizer 检查格式化后的推理输入，长度为 **37–76 tokens**，均不需截断。

词面方法不能排除改述或语义重合；没有检查完整 Alpaca 数据集，也无法检查未知的
预训练语料。五类任务与开发阶段的任务类型相近，不代表分布外能力评估。

重新检查命令（项目根目录）：

```powershell
.\.venv\Scripts\python.exe audit_quality_eval.py --check-tokenizer
```

该命令只加载本地数据和 tokenizer，不加载模型权重，不生成回答。
省略 `--check-tokenizer` 可以只做结构与词面重复检查；报告的长度字段届时为空。
重复运行会更新审核报告。出现匹配时 `status` 为 `needs_review`，应先人工检查匹配项。

## 生成入口与已生成结果

`generate_quality_eval.py` 读取本文件链接的 JSON 对象中的 `prompts`，只把每题的
`instruction` 与 `input` 传给模型；参考答案和评分标准不会进入推理输入（测试对此有断言）。
base 与各 adapter 顺序加载，每组生成结束后释放模型，三组使用相同的 greedy 设置。

```powershell
.\.venv\Scripts\python.exe generate_quality_eval.py --adapter checkpoint/lora_r8_seed42_baseline_v1/adapter_epoch_1.pt --adapter checkpoint/lora_r32_seed42_baseline_v1/adapter_epoch_1.pt
.\.venv\Scripts\python.exe generate_quality_eval.py --limit 2 --output-dir checkpoint/quality_eval_smoke
.\.venv\Scripts\python.exe generate_quality_eval.py --from-report experiments/quality_eval_v1/quality_generation.json --output-dir 目标目录
```

2026-09-21 实际运行：3 组 × 40 题 = 120 条回答，无空回答；报告中的题集哈希与上面的
v1 哈希一致，生成参数为输入上限 256、输出上限 128、greedy、bf16/CUDA。仅生成耗时
139.7 / 127.6 / 119.2 秒（base / r=8 / r=32），不含模型加载与文件写入。

产物位于 `experiments/quality_eval_v1/`：

| 文件 | 内容 |
| --- | --- |
| `quality_generation.json` | 全部回答、adapter 标识与元数据、生成参数、题集哈希、自动检查结果 |
| `quality_review_workbook.md` | 评分手册：每题一段，含题目、参考答案、三个候选回答与待填的评分行 |
| `quality_review_blind.json` | 匿名的 A/B/C 回答与评分标准，供人工盲评；与手册内容等价 |
| `quality_review_mapping.json` | 每题的标签到模型映射，评分完成前不得与评分表一起查看 |
| `quality_review_scores.json` | 已填写的评分表：120 个回答的四维 0/1/2 与理由 |

自动格式检查只覆盖 16 道有确定目标的题，每类 24 个回答：

| 检查 | 通过/总数 | base | r=8 | r=32 |
| --- | ---: | ---: | ---: | ---: |
| JSON 对象 | 8/24 | 0/8 | 4/8 | 4/8 |
| 固定行 | 6/24 | 2/8 | 2/8 | 2/8 |

base 组从不直接输出裸 JSON（0/8），两个 LoRA 组各通过一半；固定行检查三组都只通过
2/8。这只说明指定的格式属性，而且是单次 greedy 生成的结果，不能推断回答质量或一般能力。

## 评分回填流程（本轮已完成）

评分只需一份文件加一条命令：

1. 打开 `quality_review_workbook.md`，**不要**打开 `quality_review_mapping.json` 或
   `quality_generation.json`（前者给出标签到模型的映射，后者按模型标识保存回答）。
2. 每个候选回答下面有一行待填，把 `A: _ _ _ _ |` 的四个下划线换成 0/1/2，并在 `|` 后写
   一句理由。四个数字依次是正确性、完整性、格式遵循、无无据添加。
3. 填完运行回填命令：

```powershell
.\.venv\Scripts\python.exe import_quality_scores.py
```

它只读取手册与评分表，校验题集哈希、候选齐全、分值范围与理由非空；任何一处不合格都会
列出问题并**不写入**任何文件。全部合格后写入 `quality_review_scores.json`，并打印各维度
的 0/1/2 分布。它从不读取映射文件，因此盲评不会被破坏。

全部打完之后才揭示 `quality_review_mapping.json`，再据此做三模型比较。看过回答之后若
必须修改题目或评分标准，需要建立新版本，并说明原题已经成为开发数据。

## 2026-09-24 人工评分结果

120 个候选评分全部完整，分数均为 0/1/2，理由非空，题集哈希一致。
先导入评分，再读取映射；汇总工具还核对了匿名回答与模型原始回答的对应关系。
所有分数与理由保留用户原值，未进行自动修正。同题相同回答没有出现评分不一致。

| 模型 | 正确性 /2 | 完整性 /2 | 格式 /2 | 无无据添加 /2 | 总分均值 /8 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Base | 1.400 | 1.450 | 0.950 | 1.175 | 4.975 |
| r=8 | 1.475 | 1.550 | 1.325 | 1.150 | 5.500 |
| r=32 | 1.600 | 1.650 | 1.300 | 1.275 | 5.825 |

每个模型 40 个回答；各任务类别 8 个。四维总分仅为辅助的等权汇总，维度并不独立。
分项观察如下：

- 提取、格式遵循、改写的总分均值，两组 LoRA 均高于 Base。
- 摘要总分均值为 Base 6.625、r=8 6.250、r=32 6.000；完整性没有下降，
  但无无据添加的均分较低，r=32 的格式均分也较低。不能据总体均分声称每类任务都提升。
- 推理总分均值为 Base 3.875、r=8 3.375、r=32 4.250；r=8 在本组题上有所下降。
- r=8 与 r=32 有 31/40 题总分相同，分别在 4 题和 5 题上领先。
  r=32 均分高 0.325 分，同时可训练参数是 r=8 的四倍；这些观察不足以证明普遍的 rank 优势。

这里的较高/相同/较低按同题四维总分计算，不是评分者直接做的两两偏好投票。
单名评分者、少量合成题、一次 greedy 生成不能建立多评分者一致性或统计显著性。
结果支持在这些任务与评分规则下观察到有限改善，不应写成某个百分比的通用质量提升。

无需重新推理即可重新汇总：

```powershell
.\.venv\Scripts\python.exe summarize_quality_scores.py
```

工具输出汇总 JSON、Markdown、类别 CSV 和逐题 CSV，先核对全部输入再写输出。
它不修改评分源文件，并保存来源的规范化哈希。后续可选工作是增加独立评分者检验
一致性；当前所需的第一轮人工质量评估已闭环，工程上仍需验证全新环境复现。
